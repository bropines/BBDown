# Руководство контрибьютора (Contributing Guide)

Спасибо за ваш интерес к проекту BBDown! Перед отправкой изменений, пожалуйста, ознакомьтесь с этим руководством.

## Окружение для разработки

- [.NET 9.0 SDK](https://dotnet.microsoft.com/download) (или .NET 10.0 SDK в зависимости от активной ветки)
- Поддерживаемые ОС: Windows / Linux / macOS

## Сборка

```bash
# Восстановить зависимости
dotnet restore

# Собрать (Debug)
dotnet build

# Собрать (Release)
dotnet build -c Release

# Опубликовать как единый файл (пример: win-x64)
dotnet publish BBDown -r win-x64 -c Release
```

## Стиль кода

- Отступы: 4 пробела
- Кодировка: UTF-8
- Символы конца строки: Кроссплатформенные, обрабатываются автоматически средствами Git
- Соблюдайте настройки, определенные в файле `.editorconfig`

## Стратегия ветвления (Обязательно)

> ⚠️ **Ветка `master` защищена. Прямые коммиты в неё запрещены.** Все изменения должны сливаться исключительно через Pull Request.

### Правила именования веток

| Префикс | Назначение | Пример |
|------|------|------|
| `feature/` | Разработка новой возможности | `feature/drm-auto-fetch` |
| `fix/` | Исправление багов | `fix/muxer-directory-creation` |
| `refactor/` | Рефакторинг кода | `refactor/split-program-methods` |
| `docs/` | Только обновление документации | `docs/api-server-guide` |
| `deps/` | Обновление зависимостей | `deps/protobuf-3-35` |

### Процесс разработки

```bash
# 1. Создайте ветку от актуальной master
git checkout master
git pull origin master
git checkout -b feature/my-feature

# 2. Разработка и коммиты (следуйте правилам именования коммитов ниже)
git add .
git commit -m "feat: add auto cookie refresh"

# 3. Отправка ветки в удаленный репозиторий
git push origin feature/my-feature

# 4. Создайте Pull Request на GitHub и ожидайте ревью
# 5. После успешного прохождения проверок CI и получения хотя бы 1 одобрения (approve) мейнтейнер сольет ветку в master
```

### Правила написания коммитов

Следуйте стандарту [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/):

```
<type>(<scope>): <description>

[optional body]

[optional footer]
```

| Тип | Значение |
|------|------|
| `feat` | Новая возможность |
| `fix` | Исправление ошибки |
| `refactor` | Изменение кода, которое не исправляет ошибку и не добавляет новую возможность |
| `perf` | Изменение кода для повышения производительности |
| `docs` | Изменение только в документации |
| `deps` | Обновление внешних зависимостей |
| `test` | Добавление или исправление тестов |
| `chore` | Изменения в процессе сборки, конфигурации или вспомогательных инструментах |

Пример:
```
feat(drm): add auto key fetch from WVD device

Previously users had to manually provide --key and --kid.
Now the tool attempts to extract keys automatically when
a device.wvd file is present.

Closes #123
```

## Создание Issue

- Перед публикацией выполните поиск по существующим баг-репортам, чтобы избежать дублирования.
- Для сообщения об ошибках используйте шаблон Bug Report и прикладывайте лог `--debug`.
- Для предложений новых функций используйте шаблон Feature Request.

## Создание Pull Request

1. Сделайте Fork репозитория и создайте свою ветку: `git checkout -b feature/fooBar`
2. Внесите изменения и убедитесь, что `dotnet build` проходит без ошибок.
3. При необходимости обновите сопутствующую документацию (README, CHANGELOG и т.д.).
4. Закоммитьте и отправьте изменения в свой Fork: `git push origin feature/fooBar`
5. Создайте Pull Request на GitHub и заполните шаблон PR.

## Принципы ревью PR

- **Атомарность**: Один PR должен решать одну конкретную задачу.
- **Обратная совместимость**: Изменения не должны ломать существующие параметры командной строки и формат файлов конфигурации.
- **Синхронизация документации**: Изменения в коде должны сопровождаться соответствующими изменениями в документах.
- **Сборка**: Проект должен успешно компилироваться на стороне CI (0 ошибок при `dotnet build`).
- **Требования к ревью**: Любой PR (за исключением правок в документации) должен получить одобрение как минимум от 1 ревьюера.
